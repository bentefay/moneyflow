Automations domain model

What an automation is in MoneyFlow, how one is matched to a transaction, and the grouped model the mission "Refine transaction editing and simplify automation rules" proposes. Reference only; nothing here is implemented by this file.

1. One concept, three generations

"Automation" is the product name and "rule" is the domain object. They are the same thing. The vault has carried two shapes of it, and the mission proposes a third.

4. The grouped model the mission proposes

The single action becomes a set of outputs. Everything else is unchanged: the match conditions, the precedence lattice, the per-field winner, the alias indirection and the absence of links.

Fold and split are the two transformations

5. Invariants

  • No links. A transaction stores no rule id. A rule stores no transaction id. Which rule applies is a pure function of the rule list and the row.
  • Rules set values; they do not own them. A row may be edited away from its rule. That row then shows as drifted, in orange, until the rule is applied to it or changed.
  • Precedence is per field and computed in one place. Grouping changes which rule an edit extends. It never changes which rule wins a field.
  • Eligibility is per output type. Alias outputs never apply to manual rows, because they have no raw text. Tag and allocation outputs do.
  • Description text is immutable on a rule. To target different text, create a different rule.
  • Allocation is a whole set. There is no "add one person" output; an incomplete set is rejected at the boundary with no write.
  • Nothing merges silently. Migration, fold and split each either preserve the rule set or change it in a way the user chose and previewed.
