# UR-003 — Presence avatars show member name initials

- **Status:** queued
- **Source:** `specs/009-user-reported-refinements/spec.md` lines 55-74 (frozen, markerless)
- **Owning package:** P24
- **Completion:** ledger-only, after implementation and DISTINCT independent review

## Required behaviour (rule from the frozen text)

Resolve the member's display name and supply it to every presence avatar at every render site.
Initials derive from that name using the existing derivation: "Me" -> "M", "Ben Tefay" -> "BT". The
tooltip shows the resolved display name, not a key hash. Hash-derived initials remain ONLY as a
last-resort fallback when no name resolves. Avatar colour continues to derive from the stable
per-member identifier, not the name, so colour survives a rename and members sharing initials stay
visually distinct.

## Orientation (verify yourself)

`src/app/(app)/layout.tsx:218-224` and `:343` build presence users as `{ userId, isOnline: true }`
and never pass `name`. `PresenceAvatar.tsx:48` then falls back to `name || userId`, so `getInitials`
(`src/lib/utils/color.ts`) takes its hash branch (`/^[a-f0-9]+$/i` -> first 2 chars) and renders
pubkey-hash characters; the tooltip at `:56` shares that fallback. NO change to `getInitials` is
required — its word-initials branch already produces the wanted result once fed a real name. Colour
comes from `hashToColor(userId)` at `:50`; keep it keyed on `userId`.

Note: the currently-exposed value is a PUBLIC key hash, not secret material. This is a presentation
defect, not a secret-safety breach — but do not introduce any real key material into fixtures.

## Name resolution — root resolved this; verify it

Both this requirement and UR-006 (`tasks/ur-006.md`, package P27, vault members listed by name) need
the SAME lookup: from a member's `pubkeyHash` to a human-readable display name. The machinery
already exists and must be reused rather than reinvented:

- `personSchema` (`src/lib/crdt/schema.ts:44-51`) carries `linkedUserId`, documented as "links to a
  user's pubkeyHash". That is the JOIN KEY from a vault member to a person record.
- `resolvePersonDisplayName` (`src/lib/crdt/person.ts:42`) already implements the fallback ladder:
  trimmed `name` if present, else `memberFallbackName(linkedUserId)`, else "Unnamed". Its own doc
  comment says to use it for display rather than reading `name` directly.

So the shape is: find the person whose `linkedUserId` equals the member's `pubkeyHash`, then call
`resolvePersonDisplayName`. Do NOT add a second name-resolution path, and do NOT read `person.name`
directly.

Extract ONE shared pure helper that both the presence avatar and the vault members list can use, so
the two surfaces cannot drift apart. Whichever of P24 or P27 lands first creates it; the second
reuses it. If you are second and find the helper already present, reuse it and say so in evidence.

**Root checked what the existing fallback actually renders, and it needs a decision.**
`memberFallbackName` (`src/lib/crdt/person.ts`) returns `` `Member ${pubkeyHash.slice(0, 8)}` `` —
e.g. `"Member 3f2a9b1c"`. Two consequences you must handle deliberately rather than inherit:

1. Fed to the existing `getInitials`, `"Member 3f2a9b1c"` yields **"M3"** — the first letters of two
   "words", the second of which is hash text. That is better than raw hash characters but is not a
   name-derived initial in any meaningful sense.
2. The frozen text says a raw public key hash is never the visible label and that where no display
   name resolves, a clearly human-readable fallback is shown. `"Member 3f2a9b1c"` is arguably
   human-readable as a TOOLTIP, while "M3" as AVATAR INITIALS is not obviously better than the "AD"
   the principal reported.

Decide and justify in evidence: what the avatar shows when no name resolves. A single "M", a person
icon, or something else are all defensible; silently inheriting "M3" is not. Whatever you choose,
the tooltip and the accessible name must agree with it, and the ordinary named case must still
produce "M" for "Me" and "BT" for "Ben Tefay". Do NOT change `memberFallbackName` itself without
checking its other callers. Root already checked: besides `resolvePersonDisplayName`, it is called
at `src/components/features/transactions/TransactionRow.tsx:222`, where it is mapped over presence
pubkey hashes to build the row's presence label. So it IS load-bearing for a second surface and
changing it would silently alter presence row labels too. Prefer changing what the AVATAR does with
an unresolved name over changing the shared fallback.

## Root verified the join actually works — and found the caveat that decides this package

`linkedUserId` is genuinely POPULATED, not merely declared: `ensureMemberPerson`
(`src/lib/crdt/person.ts:76`) writes `linkedUserId: pubkeyHash` when it creates a person for a vault
member, and it has 3 caller files. `resolvePersonDisplayName` has 10 caller files, so it is the
established display path. `deriveMemberPersonId` gives a DETERMINISTIC person id from a pubkey hash,
which may let you look the person up directly rather than scanning `people` for a matching
`linkedUserId` — check which is correct in context.

**THE CAVEAT, and it is the crux of this package:** `ensureMemberPerson` creates the member person
with `name: undefined`. The schema comment at `schema.ts:46` says so explicitly — "auto-created
member people (HS-012) start unnamed". So for a member who has never been given a name, the join
SUCCEEDS and still yields no name, and `resolvePersonDisplayName` falls through to
`memberFallbackName` -> `"Member 3f2a9b1c"` -> initials "M3".

That is precisely the principal's situation: they reported their name is the default "Me" and the
avatar showed "AD". So do NOT assume the join alone fixes the reported defect. Establish empirically
what the principal's own member person actually holds — a real name, the literal "Me", or
`undefined` — and make the unnamed case render something defensible. If the name genuinely is "Me",
the join fixes it and initials become "M". If it is `undefined`, the join alone changes "AD" to "M3"
and the frozen text is still not satisfied. Report which case holds in evidence.
