# UR-005 — Transaction table chrome is minimal at rest

- **Status:** queued
- **Source:** `specs/010-user-reported-refinements-2/spec.md` lines 11-24 (frozen, markerless)
- **Owning package:** P26

Remove the resting background fill from the date, description, account, status, percentage and
amount cells so the table reads as clean and minimal. KEEP every state treatment: hover, focus,
focus-visible, selected, editing, presence and validation. Focus must remain obviously visible.
Contrast stays at least WCAG AA and the accessible role/name/state of each cell is unchanged.

Verify against `TransactionRow.tsx` and the cell components under
`src/components/features/transactions/cells/`. This is a styling change; do not alter behaviour.

## Root traced the actual source — VERIFY, and do not assume it is where it looks

Root looked for the resting fill and it is NOT where a reader would first expect. Establish this
yourself before changing anything:

- **The cells are already clean at rest.** Every inline cell input sets `bg-transparent` with
  `border-transparent` and `shadow-none`, and their `bg-accent/30` is `hover:`-SCOPED, not resting —
  see `InlineEditableAmount.tsx:270`, `InlineEditableDate.tsx:208`, `InlineEditableStatus.tsx:101`,
  and `InlineEditableDescriptionAlias.tsx:268-270`.
- **The row container is also hover/focus-scoped**: `TransactionRow.tsx:314-324` carries
  `hover:bg-accent/50 focus:bg-accent/50`, with `bg-accent` only when `isSelected` and a yellow tint
  only when `isDuplicate`. No zebra striping exists anywhere in the table.
- **ROOT CONFIRMED THE SOURCE EMPIRICALLY — this is no longer a hypothesis.** The shared shadcn
  `Input` base at `src/components/ui/input.tsx:11`, which carries `dark:bg-input/30`
  UNCONDITIONALLY, plus `border` and `shadow-xs`. A local `bg-transparent` in the cell's `cn(...)`
  does not necessarily win against it, and `dark:bg-input/30` is a resting fill by construction.
  That is root's leading hypothesis, NOT a finding — confirm it in the running app with devtools
  before acting, and say in evidence what you observed.

**This matters for scope.** If the fill comes from the shared `Input` primitive, then changing
`input.tsx` would alter EVERY input in the product, not just the transaction table — settings forms,
dialogs, filters. That is almost certainly wrong for a requirement scoped to the transaction table.
Prefer overriding at the table's cells, or introducing a variant, over editing the shared primitive.
If you conclude the shared primitive genuinely must change, stop and report to root rather than
widening the blast radius silently.

Note also `TransactionRow.tsx:566` carries `bg-muted/30` on the expanded-row detail area — decide
deliberately whether that is in scope, since the frozen text names the date, description, account,
status, percentage and amount cells specifically.

## Root's empirical proof of the mechanism — reproduce it, then design

The cells DO render the shared primitive: `InlineEditableAmount.tsx:16` imports `Input` from
`@/components/ui/input` and renders it at `:255`. The other inline cells follow the same pattern.

`cn` is `twMerge(clsx(...))` (`src/lib/utils.ts:5`), and **`twMerge` does NOT treat a bare
`bg-transparent` as conflicting with a variant-prefixed `dark:bg-input/30`** — they target different
states, so both survive the merge. Root ran it:

```
twMerge('dark:bg-input/30 border bg-transparent', 'h-7 border-transparent bg-transparent shadow-none')
  -> 'dark:bg-input/30 border h-7 border-transparent bg-transparent shadow-none'
```

`dark:bg-input/30` SURVIVES. And `--input` in dark mode is `oklch(1 0 0 / 15%)`
(`src/app/globals.css:118`), i.e. 15% white — so in dark mode every inline cell renders a visible
resting fill that the cell's own `bg-transparent` cannot remove. The shared base also contributes
`border` and `shadow-xs`.

**Reproduce this yourself before designing**, and confirm in the running app which theme the
reported chrome appears in. If the fill is dark-mode-only, say so explicitly in evidence — the
frozen text does not scope itself to a theme, so a fix that only works in one is incomplete.

**Do NOT edit `src/components/ui/input.tsx`.** It is the shared primitive behind every input in the
product — settings, dialogs, filters — and this requirement is scoped to the transaction table.
Override at the cell layer, e.g. by adding `dark:bg-transparent` alongside the existing
`bg-transparent`, or by introducing a variant. Verify your chosen approach actually wins under
`twMerge` rather than assuming it does; the whole reason this defect exists is that an
obvious-looking override silently did not.
