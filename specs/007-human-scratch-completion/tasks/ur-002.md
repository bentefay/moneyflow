# UR-002 — Transaction search matches alias-resolved descriptions

- **Status:** queued
- **Source:** `specs/009-user-reported-refinements/spec.md` lines 35-53 (frozen, markerless)
- **Owning package:** P23
- **Completion:** ledger-only, after implementation and DISTINCT independent review

## Required behaviour (rule from the frozen text)

Search must match the description text the user can see. It matches the alias-resolved description
when a transaction has a description alias, AND continues to match the raw stored description so
pre-alias imported text stays findable, AND continues to match notes. Alias resolution follows the
one-hop symlink relationship so matching agrees with what the table displays. Matching stays
case-insensitive and substring-based.

## Orientation (verify yourself)

The defect: `filterTransactions` at `src/lib/crdt/queries.ts:560-567` matches only `tx.description`
and `tx.notes`. Case handling is already correct — both sides are lowercased; the bug is the FIELD
read, not case sensitivity. Displayed text is resolved via `descriptionAliasId` through
`aliasLookup.resolve(...)` (`src/app/(app)/transactions/page.tsx:337-338`, `:398-399`); aliases form
a one-hop symlink graph (`src/lib/crdt/schema.ts:87-94`). Manual rows are created with
`description: ""` (`page.tsx:557`), which is why an aliased manual row is unfindable today.

Design note: `filterTransactions` is a pure query with no alias lookup in scope. Thread the resolver
in or lift the search predicate — keep the function pure and the data immutable. This is a real
design choice; record the approach in evidence.
