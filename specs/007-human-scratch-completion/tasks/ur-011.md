# UR-011 — The header checkbox selects every row matching the filters

- **Status:** queued
- **Source:** `specs/012-transaction-selection/spec.md` lines 31-55 (frozen, markerless)
- **Owning package:** P32

## Root's read, to VERIFY rather than trust

`TransactionTable.tsx:270` derives `filteredIds` as `transactions.map((t) => t.id)` from the
`transactions` prop. Establish FIRST what that prop actually contains at the call site: the page
computes `filteredTransactions` and then
`displayedTransactions = filteredTransactions.slice(0, displayCount)` with `PAGE_SIZE = 50`
(`src/app/(app)/transactions/page.tsx:78`, `:282-284`). If the table receives the DISPLAYED slice,
then select-all currently selects only the loaded page and the principal's report is a real defect.
If it receives the full filtered list, the defect is narrower — possibly only in how the header's
own checked/indeterminate state is derived. Determine which before designing anything, and say so in
evidence.

Note also: `selectAll` in `hooks/useTableSelection.ts` contains a `console.log` left in the shipped
code. Remove it as part of this work.

## Required behaviour

Rule from the frozen text. In summary: the header checkbox selects every transaction matching the
active filters including unrendered and not-yet-paged rows; clearing clears that same set; the
checkbox reflects the whole filtered set as selected, indeterminate or clear; changing filters
re-derives that set; and bulk actions afterwards apply to every selected transaction.

**Efficiency is part of the requirement, not a nice-to-have.** Selecting all must not force rows to
render, must not page in rows merely to enumerate them, and must stay responsive at a hundred
thousand transactions. Neither the selection nor the header state may be derived by a scan costing
rendered-rows x matching-rows. Consider whether a materialised `Set` of every matching id is the
right representation at that scale, or whether a select-all-with-exceptions model serves better;
justify the choice in evidence against the stated scale rather than by assertion, and measure it.

Keep the hook pure and its data immutable.

## Tests

Unit coverage for: select-all over a filtered set larger than the rendered window; clear-all; the
three header states; re-derivation after a filter change; and bulk action reaching an unrendered
row. A performance assertion at the stated scale, in the style of the existing large-import tests.
E2E asserting select-all then a bulk action affects rows that were never scrolled into view.

Do NOT copy the wall-clock RATIO style of `tests/unit/import/duplicates.test.ts:724-749` — it is
load-sensitive by construction and is already a recorded carry-forward defect (`Q-P23-01-01`).
Prefer an absolute bound or an operation count.
