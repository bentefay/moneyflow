## Root's findings — VERIFY each, do not trust

Root has had several readings corrected by workers in this goal, so check these yourself.

**Row click is a NO-OP today, so nothing is lost by shrinking the row's own hit area.**
`TransactionRow.tsx:310` fires `onClick={() => onClick?.()}`, wired through
`TransactionTable.tsx:536` to `handleRowClick` -> `onTransactionClick`. But `onTransactionClick` is
never supplied: `grep -n 'onTransactionClick' 'src/app/(app)/transactions/page.tsx'` returns
nothing. The principal reported the same thing independently — "clicking the row doesn't seem to do
anything". Confirm before relying on it; if you find a caller, the trade-off changes and you must
report it.

**Where the dead space comes from.** The row is `grid items-center gap-4 px-4 py-3`
(`TransactionRow.tsx:315`) while the inline controls are `h-7`. With 12px of vertical row padding
against a 28px control there is a dead strip above and below each control, plus horizontal `gap-4`
between cells. Cell wrappers such as the description cell at `TransactionRow.tsx:376-380`
(`flex min-w-0 items-center gap-1` with an inner `min-w-0 flex-1`) add their own boxes. Establish
the real geometry in the running app with devtools rather than reasoning only from classes.

**The principal has already answered the per-cell question**, and the frozen text records it: every
cell has a logical equivalent. The checkbox keeps its drawn size while its hit area spans the cell;
the date keeps its text and icon in place while its hit area grows; likewise the status select, tag
chooser, amount and percentage fields.

## Constraints

- **Resting appearance must not change.** Same size, position, alignment, typography, spacing. If a
  screenshot at rest differs, the change is wrong. Prefer moving padding from the wrapper onto the
  control over resizing anything.
- **Do NOT edit the shared shadcn primitives** in `src/components/ui/` — they back every input in
  the product. P26 established this constraint and honoured it; the same applies here. Work at the
  cell and wrapper layer.
- **Hover feedback WILL change**, because the hover region follows the enlarged control. That is
  required by the frozen text, not a regression — but state it explicitly in evidence so a reviewer
  is not left wondering, and confirm the resting appearance is genuinely untouched.
- **Do not regress P26 (UR-005).** Resting cells must still paint `rgba(0,0,0,0)` in BOTH themes.
  `RESTING_CELL_CHROME` (`src/components/features/transactions/cells/cell-chrome.ts`) is applied at
  five cell sites; enlarging a control must not reintroduce a resting fill or border.
- **Do not regress UR-001 (P22).** Add-transaction focuses the new row's description via a monotonic
  `focusin` latch. A larger hit area must not let a stray click steal that focus, and
  `tests/e2e/helpers/settlement.ts`'s `addEmptyTransaction` must keep working.
- Keyboard behaviour, tab order, arrow-key grid navigation and the focus ring are unchanged, and the
  focus ring stays clearly visible. Accessible roles, names and states are unchanged, and each cell
  must still expose exactly ONE control to assistive technology — watch for a wrapper that becomes
  independently clickable and adds a second interactive node.
- Retain per-cell behaviour: the description cell's alias proposal controls, the row presence
  indicator, and the expanded-row toggle.
