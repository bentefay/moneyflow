# UR-006 — Vault members are listed by name

- **Status:** queued
- **Source:** `specs/010-user-reported-refinements-2/spec.md` lines 26-38 (frozen, markerless)
- **Owning package:** P27

Vault Settings must list each member by display name, never by a raw public key hash. Resolve the
name the same way UR-003 resolves it for the presence avatar, so the two agree. Where no name
resolves, show a human-readable fallback rather than a bare hash. Tooltips and accessible names
follow the same rule as the visible label.

Related: UR-003 (`tasks/ur-003.md`, package P24) fixes the same class of defect for presence
avatars. Prefer a single shared resolution helper over two independent implementations.

## Name resolution — root resolved this; verify it

Identical to UR-003 (`tasks/ur-003.md`, package P24). Root confirmed the current members list labels
each member with `shortenPubkeyHash`
(`src/components/features/vault/AccessMembersSection.tsx:28-29`, rendered at `:130` and in the
`aria-label` at `:152`) — a truncated hex hash, which is exactly what the frozen text forbids.

The join already exists: `personSchema` (`src/lib/crdt/schema.ts:44-51`) carries `linkedUserId`,
documented as "links to a user's pubkeyHash", and `resolvePersonDisplayName`
(`src/lib/crdt/person.ts:42`) implements the fallback ladder. Find the person whose `linkedUserId`
equals the member's `pubkeyHash`, then resolve. Do NOT read `person.name` directly and do NOT add a
second resolution path.

Use the SAME shared pure helper as P24 so the members list and the presence avatar cannot drift.
Whichever package lands first creates it; the second reuses it and says so in evidence. Note the
frozen text requires the ACCESSIBLE NAME to follow the same rule as the visible label, so the
`aria-label` at `:152` must change too, not just the visible text.

## The shared helper NOW EXISTS — reuse it, and root already checked the data access

P24 landed `resolveMemberDisplayName` in `src/lib/crdt/person.ts:99`. Verify its current signature
yourself, but as at this writing it is:

```
resolveMemberDisplayName(
    people: Readonly<Record<string, LinkedPerson | undefined>>,
    pubkeyHash: string
): MemberDisplayName
```

returning the discriminated union `MemberDisplayName` (`person.ts:42`), i.e. `{kind:"named",name}`
or `{kind:"unnamed"}`. It scans for a person whose `linkedUserId` matches, skipping soft-deleted
people, and uses the extracted `personOwnName` rung. **Reuse it. Do NOT add a second resolution
path** — the whole point of P24 extracting it was that the members list and the presence avatar
cannot be allowed to drift apart.

**Root checked the data-access question so you do not have to discover it mid-implementation.**
`AccessMembersSection` currently takes NO props (`:40`) and is rendered bare from
`src/app/(app)/settings/page.tsx:28`, so it has no `people` today. But `usePeople()`
(`src/lib/crdt/context.tsx:701`, a `useVaultSelector` over `state.people`) is directly available,
because the settings page renders inside `VaultProvider` — see `src/app/(app)/layout.tsx:96-101`,
where `ActiveVaultProvider` wraps `VaultProvider` wraps `{children}`. So calling `usePeople()`
inside the component is the straightforward route and NO prop threading is required. Confirm this
yourself before relying on it.

**What to replace.** `shortenPubkeyHash` (`AccessMembersSection.tsx:28-29`) renders `3f2a9b1c…4d5e`.
It has exactly two call sites: the visible label at `:130` and the `aria-label` at `:152`. The
frozen text requires the accessible name to follow the same rule as the visible label, so BOTH must
change. Once both are replaced, `shortenPubkeyHash` becomes dead — delete it rather than leaving an
unused helper, and confirm with a grep that nothing else calls it.

**The unnamed case.** P24 ruled that an unnamed member's AVATAR shows a person icon with the label
"Unnamed member", and deliberately did NOT change `memberFallbackName` because
`TransactionRow.tsx:222` still uses it for the row presence label. Decide what the members LIST
shows for `{kind:"unnamed"}` and justify it. Consistency with P24's "Unnamed member" is the obvious
choice; whatever you pick, the visible label and the accessible name must agree, and neither may
contain hash characters.
