# UR-008 — CSV import parity with OFX, and honest import counts

- **Status:** queued
- **Source:** `specs/010-user-reported-refinements-2/spec.md` lines 56-86 (frozen, markerless)
- **Owning package:** P29

CSV and OFX exports of the same activity must import identically, and the summary must describe its
counts truthfully.

## Confirmed root cause for the reported errors

`parseAmount` in `src/lib/import/csv.ts:165-190` strips currency symbols, handles accounting
parentheses and handles a leading `-`, but has NO branch for a leading `+`, so `+69.00` fails
magnitude validation and the row is reported as an error. The principal's CSV contains EXACTLY 15
such rows, which matches the 15 errors reported. Fix the parser to accept an explicit plus sign.

Also verified in that file: 10 rows carry a quoted description containing a comma
(`"PAYMENT RECEIVED, THANK YOU"`), so quoted-delimiter handling must keep them as one field.

## Observed current summary, reported by the principal 2026-08-01

Re-importing the CSV after the OFX had already been imported produced:

```
622  Total Rows
0    Valid
15   Errors
607  Duplicates / Will be marked
0    Old
```

Read this carefully before implementing. It tells us three things:

1. The partition already holds arithmetically: `0 + 15 + 607 + 0 = 622`. Nothing is double-counted
   or missing in THIS run.
2. Five labels already exist — Total Rows, Valid, Errors, Duplicates with a "Will be marked"
   qualifier, and a single `Old`. The gap versus the required set is that one `Old` bucket must
   SPLIT into **Old New (excluded)** and **Old Duplicates (excluded)**.
3. `0 Valid` is CORRECT here and must not be "fixed": the same 622 transactions were already
   imported from the OFX file, so every parseable row is genuinely a duplicate. This run is not the
   confusing one.

The confusing run the principal originally reported was a DIFFERENT configuration — a 10-day cutoff
with skip-old-if-duplicate — which produced `561 old, 46 duplicates, 15 errors`. There, `old`
conflated old-and-new with old-and-duplicate, which is exactly what the split fixes. Both runs must
partition Total Rows under the six required labels.

The 15 Errors are constant across both runs, consistent with the confirmed leading-plus defect.

## Other required behaviour

- `collapseWhitespace` defaults to TRUE for new imports of every supported type. It is currently
  `false` at `src/lib/import/types.ts:154`.
- Column detection runs AUTOMATICALLY when a delimited file loads, and works with NO header row.
- Detection is value-driven: parses-as-date is the date column, parses-as-amount once symbols and
  signs are handled is the amount column, remaining text is the description.
- Date-format detection works from values alone, including day-first `dd/MM/yyyy`, with no header.
- The summary must report EXACTLY these six categories, with these labels, as specified by the
  principal on 2026-08-01 and recorded in QUESTIONS.md under Q-UR008-02:
    - **Total Rows**
    - **Valid**
    - **Errors**
    - **Duplicates (will be marked)** — these ARE imported, and marked as duplicates
    - **Old New (excluded)** — older than the cutoff, not duplicates, NOT imported
    - **Old Duplicates (excluded)** — older than the cutoff AND duplicates, NOT imported Keep the
      parenthetical qualifiers: they are what tell the user whether a row is imported. The five
      outcome categories must PARTITION Total Rows — every row lands in exactly one, no row counted
      twice, none omitted. The principal reported `561 old, 46 duplicates, 15 errors` as confusing
      precisely because `old` conflated Old New with Old Duplicates.

## Root traced ALL FOUR reported problems to their causes — verify each, do not trust

Root has had several readings corrected by workers in this goal. Reproduce these before designing.

**1 and 2 — auto-detect did not run, and got it wrong when clicked. ROOT CAUSE: detection matches on
HEADER NAMES, and the principal's file has NO HEADER ROW.**

- `autoDetectMappings` (`src/components/features/import/tabs/MappingTab.tsx:63`) and
  `autoDetectColumnMappings` (`ColumnMappingStep.tsx:248`) both take `headers: string[]` and match
  substrings like `"date"`, `"amount"`, `"debit"`. With no header row there is nothing to match, so
  detection cannot succeed regardless of when it runs.
- Both are invoked ONLY from a click: `ColumnMappingStep.tsx:155` and `MappingTab.tsx:224`. Nothing
  runs them on load, which is the principal's first complaint.
- **So the frozen requirement that detection be VALUE-DRIVEN is not a refinement of the existing
  approach — it is a different approach.** Parses-as-date is the date column, parses-as-amount once
  symbols and signs are handled is the amount column, remaining text is the description. Note there
  are TWO detection implementations; establish which is live in the import wizard the principal used
  before changing either, and say so in evidence.

**3 — date format detection failed. ROOT CAUSE: a single-sample heuristic.**
`FormattingStep.tsx:90-99` reads ONE sample and, for `dd/MM/yyyy` versus `MM/dd/yyyy`, guesses by
whether the first part exceeds 12. Root measured the principal's file: **240 of its 622 rows have a
first field <= 12**, so a sample drawn from those is genuinely ambiguous in isolation. The file's
FIRST row is `30/06/2026`, which that heuristic WOULD resolve correctly — so the detector reporting
failure is consistent with it never having run, not with it running and guessing wrong. Establish
which occurred. The fix is to decide from the whole column, not one sample: a column containing any
value with a first part above 12 is day-first; a column where all values are ambiguous needs a
documented tie-break rather than a silent guess.

**4 — the 15 errors. ROOT CAUSE CONFIRMED, and it is a one-branch omission.** `parseAmount`
(`src/lib/import/csv.ts:165-200`) strips currency symbols, handles accounting parentheses at
`:177-180` and handles a leading `-` at `:182-186`, then validates the magnitude — but there is NO
branch for a leading `+`, so `+69.00` fails `isWellFormedMagnitude` and the row is reported as an
error. The principal's file contains exactly 15 such rows, matching the 15 errors reported. OFX was
unaffected because `<TRNAMT>` carries no plus sign.

**`collapseWhitespace` is `false` at `src/lib/import/types.ts:154`**, confirming the default must
change.

## Scale note for the E2E

The principal's file is 622 rows. A fixture of that size in an E2E is slow; a fixture of five rows
cannot exercise the whole-column date inference that requirement 3 needs. Choose deliberately and
justify the choice — a column of ambiguous dates plus one disambiguating value is the minimum that
proves whole-column inference, and it need not be 622 rows to do so.

## CORRECTIONS to root's analysis, established by `p29-implementer-01` and re-verified by root

Root's four mechanism claims were checked against unmodified code. **Two confirmed, two DISPROVED.**
The disproofs matter because they change the shape of the fix.

**CONFIRMED — the leading-plus defect**, but the function is **`parseNumber`** at
`src/lib/import/csv.ts:164-209`, NOT `parseAmount`. (`parseAmount` exists only at
`src/components/features/automations/rule-editor-model.ts:160` and is unrelated.) Observed:
`parseNumber("+69.00") = NaN`, `parseNumber("-69.00") = -69`, `parseNumber("(69.00)") = -69`.

**CONFIRMED — `collapseWhitespace` defaults false**, with a SECOND site root did not name:
`src/lib/crdt/schema.ts:242` also defaults it false for persisted templates. Both must change.

**DISPROVED — "nothing runs detection on load" is FALSE.** Root verified the implementer's
correction: `src/hooks/use-import-state.ts:347` calls `autoDetectColumnMappings(headers)` on file
load and `:351` calls `detectFormatting(...)`. **Detection DOES run unprompted today.** It cannot
SUCCEED on a headerless file because `parseRawRows` synthesises `["Column 1".."Column 4"]`, and
`autoDetectColumnMappings(["Column 1",…]) = {}` was observed.

**This makes it ONE cause, not two — and it settles root's "establish which occurred" question.**
With `{}` mappings, `detectFormatting`'s `sampleColumn(..., "date")` returns `[]`, so
`detectDateFormat([])` returns `null` and the format stays at the default `yyyy-MM-dd`. **The date
detector never received a sample.** It ran and got empty input. Root's 240-of-622 measurement is
correct — the implementer re-measured independently and got 240 with first-part <= 12, 382 above,
first row above — but it is a RED HERRING for the reported failure:
`detectDateFormat(["30/06/2026"])` returns `"dd/MM/yyyy"` correctly. The single-sample heuristic
remains a real latent defect and the frozen text still requires whole-column inference; it simply is
not what the principal hit.

**DISPROVED — the file root cited for the date heuristic is DEAD CODE, and there are THREE
implementations, not two.** Root verified: `grep -rn '<ColumnMappingStep\|<FormattingStep'` returns
NOTHING — neither component is ever mounted; only their helper exports are consumed. So
`FormattingStep.tsx:90-99`, which root cited as the live heuristic, is unreachable. The LIVE
single-sample heuristic is `detectDateFormat` at
`src/components/features/import/tabs/FormattingTab.tsx:85-119` — root confirmed the identical
`firstPart > 12` logic at `:98`, `:104` and `:115`, duplicated in the dead file at `:95` and `:98`.

**Authoritative answer to "which is live":** `autoDetectColumnMappings`
(`ColumnMappingStep.tsx:248`, consumed by the hook) plus `detectDateFormat` / `detectNumberFormat`
(`tabs/FormattingTab.tsx`). `MappingTab.autoDetectMappings:63` is a THIRD header-name
implementation, reachable only behind the tab's Auto-detect button. `FormattingStep`'s copy is dead.

**Two further facts about the principal's file, from the implementer's independent re-measurement:**
column 3 is EMPTY on every row — value-driven detection must not mistake an empty column for the
description — and **611 of 622 descriptions contain a run of consecutive spaces**, which makes the
`collapseWhitespace` default materially load-bearing for this file rather than incidental.
