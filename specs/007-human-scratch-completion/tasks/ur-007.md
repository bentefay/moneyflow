# UR-007 — Dates display in the browser's locale

- **Status:** queued
- **Source:** `specs/010-user-reported-refinements-2/spec.md` lines 40-54 (frozen, markerless)
- **Owning package:** P28

Dates must render in the viewer's resolved locale, not a fixed US format. Same-year dates show day
and month only; different-year dates and any date shown while editing include the year in full. Date
entry accepts what the same locale displays. Storage and comparison are unchanged: dates are
calendar dates and no displayed value may shift due to a time zone.

Because the browser reports its LANGUAGE rather than the viewer's regional format, and no web API
exposes the latter, a per-viewer setting overrides the presentation: follow the browser, day first,
month first, or year first. The calendar picker follows that choice too, week start included.

Note the environment lesson from UR-004: locale and time zone are different signals. This
requirement is explicitly about the browser's resolved LOCALE for date presentation.

## Root's finding: MOST OF THIS MAY ALREADY BE IMPLEMENTED — investigate before rewriting

Do not assume this is a hardcoded-US-format defect. Root read the code and found the opposite of
what the report implies. VERIFY all of this yourself; root has had several readings corrected in
this goal.

`formatTransactionDate` (`src/lib/utils/date-format.ts`) ALREADY does substantially what UR-007
requires:

- resolves `locale ?? navigator.language` (falling back to `en-GB`, not `en-US`);
- same year -> `day: "numeric", month: "numeric"` with leading zeros stripped, i.e. D/M with NO
  year;
- different year above 2000 -> adds `year: "2-digit"`, i.e. D/M/YY;
- year <= 2000 -> full `DD/MM/YYYY`. It uses `toLocaleString` for ORDER and SEPARATOR rather than a
  hardcoded pattern, so an `en-AU` viewer should already get day-first.

`InlineEditableDate.tsx:118` uses it for the compact display, and `formatDateFull` at `:46-53`
handles the EDITING presentation with `day/month: "2-digit", year: "numeric"` on
`navigator.language` — note that is a FOUR-digit year, where the frozen text requires TWO digits
while editing.

**So the likely real defects are narrower than "dates are US format", and your first job is to find
out which actually reproduce:**

1. **Editing shows a 4-digit year** where `spec.md:50` requires two digits. This one is visible in
   the code at `formatDateFull`.
2. **Date ENTRY parsing.** `spec.md:51-52` requires that a value can be typed back in the form it
   was displayed. Check what the input actually accepts — if it parses ISO or a fixed pattern rather
   than the locale form it just rendered, that is a real defect and probably the one the principal
   hit.
3. **Whether the principal's browser locale is what they expect.** UR-004 established that this
   machine runs `LANG=en_US.UTF-8` while sitting in `Australia/Brisbane`, and that
   `navigator.language` is therefore `en-US`. If date display keys off `navigator.language`, an
   `en-US` browser will correctly render US-ordered dates even though the user is Australian. **That
   would mean the display code is working exactly as written and the requirement is really about
   which SIGNAL to use** — exactly the distinction UR-004 drew for currency. Establish empirically
   what `navigator.language` resolves to in the principal's browser before designing a fix, and
   record it.
4. Other surfaces: `ImportTable.tsx:339` uses the same helper; check People, accounts and any date
   shown outside the transaction table.

**If you conclude the display code already satisfies the frozen text and only the editing year and
entry parsing need changing, say so plainly and scope the package accordingly.** Do not manufacture
a larger change to match the report's framing. Equally, if you find the locale signal is the real
issue, that interacts with UR-004's reasoning and you should say so rather than silently choosing a
signal.

Existing coverage lives at `tests/unit/domain/date-format.test.ts` — read it first; it likely
already pins several of the clauses above.
