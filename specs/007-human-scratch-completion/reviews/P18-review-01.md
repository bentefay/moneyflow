## 4. Contract correctness vs primary sources — PASS, with two evidence-accuracy findings

I re-verified the vendor/spec claims against primary sources rather than the implementer's summary.

**Confirmed verbatim:**

- WHATWG defines `new-password` as "A new password (e.g. when creating an account or changing a
  password)" and `current-password` as "The current password for the account identified by the
  username field (e.g. when logging in)"; `username` is a defined autofill field name. The chosen
  tokens are correct for the two surfaces.
- MDN: "In most modern browsers, setting `autocomplete` to `"off"` will not prevent a password
  manager from asking the user if they would like to save username and password information".
- Apple: "Safari ignores `autocomplete="off"`", and Apple does recommend `<form>` grouping even when
  submission is implemented in JavaScript.
- 1Password documents `data-1p-ignore`, documents the CSS-hidden `autocomplete="username"` anchor
  pattern, and warns that a `get` submission "could unintentionally leak credentials in the URL"
  because the extension "will automate a button click with `element.click()`". The `method="post"`
  choice is therefore a genuine secret-safety control, correctly attributed.
- Bitwarden `data-bwignore` confirmed in first-party source (`collect-autofill-content.service.ts`:
  `let inputQuery = "input:not([data-bwignore])";`), and submission detection "by attaching an event
  to each form `submit()` button on the DOM" confirmed in Bitwarden's contributing docs.

**See NB-1 and NB-2** for two claims that do not survive primary-source checking.

## Findings

No finding below is blocking. Each is recorded with file:line and a concrete scenario.

### NB-1 (NON-BLOCKING, evidence accuracy) — the WHATWG "no normative statement" correction is itself wrong

`evidence/P18/implementation-01.md:149-151` asserts: "**WHATWG contains no normative statement that
UAs may ignore `autocomplete=off` for password fields** — that claim is MDN/vendor-level only".

Primary-source check contradicts this. The WHATWG autofill section contains normative permission: "A
user agent **may** allow the user to override an element's autofill field name, e.g. to change it
from 'off' to 'on' … despite the page author's objections", and "user agents **may** in particular
consider replacing the autofill field name of form controls that match the description given in the
first column of the following table, when their autofill field name is either 'on' or 'off'" — a
table that maps a password-state input preceded by an `autocomplete="username"` field to
`current-password`.

The implementer is right on one narrower point: the string "password manager" does not appear in the
spec, so the _framing_ is MDN/vendor-level. But the normative "may override `off` on password
fields" language does exist.

**Failure scenario:** a future package reads this evidence, believes the spec is silent, and adopts
a weaker justification or an unnecessary workaround for an `autocomplete=off` concern the spec
already addresses.

**Why non-blocking:** no product behavior depends on it. The implementation does not rely on
`autocomplete=off` being ignored — it deliberately introduces a separate canonical field, which is
correct under either reading. This is a documentation-accuracy defect in the evidence file only.

### NB-2 (NON-BLOCKING, evidence accuracy) — Chromium hidden-username guidance is overstated

`evidence/P18/implementation-01.md:133-136` states that Chromium's "Create Amazing Password Forms"
doc "directs authors to 'include a hidden input field containing this information even if it is not
directly necessary for your form'".

The current first-party guidance (web.dev _Sign-in form best practices_) recommends a hidden
username input **conditionally** — for two-page sign-in flows: "the form on the second page should
have a hidden input element with the email value, to help enable password managers". It is not an
unconditional directive, and the article's preferred approach is a single form with JS show/hide.

**Failure scenario:** a reader treats an unconditional Chromium mandate as the basis for the anchor
field, and is surprised when Chromium's documented rationale does not cover this shape of form.

**Why non-blocking:** the pattern itself is independently and unambiguously supported by 1Password's
first-party docs, which show exactly this CSS-hidden `autocomplete="username"` field and explain the
matching rationale. The implementation is correct; only one of its three citations is over-read. The
observed behavior (one username anchor, one password field, same form) is what all three engines
parse.

### NB-3 (NON-BLOCKING, already disclosed) — `data-lpignore` has no first-party source

`src/components/features/identity/SeedPhraseInput.tsx:354` sets `data-lpignore="true"` on each word
input. I could not obtain any quotable first-party lastpass.com text confirming the attribute; the
support site is JS-rendered and returned no extractable content. Only secondary sources support it.

**Failure scenario:** LastPass does not honour the attribute and offers to fill individual word
inputs.

**Why non-blocking:** the implementer disclosed this precisely and correctly in Q-PROPOSAL-P18-01-2
rather than overclaiming. An unrecognized `data-*` attribute is inert — it cannot cause a
regression. The load-bearing defense against per-word filling is structural (twelve `type="text"`
fields with a single separate canonical password field), not attribute-based.

### NB-4 (NON-BLOCKING, evidence methodology) — the dark-mode observation does not test dark mode

`evidence/P18/implementation-01.md:356-357` reports verifying dark mode via
`emulateMedia({ colorScheme: "dark", reducedMotion: "reduce" })` and concludes "both media queries
matched … credential styled correctly".

This project's dark variant is **class-based**, not media-query-based: `src/app/globals.css:4`
declares `@custom-variant dark (&:is(.dark *))`, and `.dark` is defined at `globals.css:84`.
`emulateMedia({colorScheme:'dark'})` does not add the `.dark` class, so no dark styling is
activated. I reproduced this: measured computed colors for the validation indicators were
**byte-identical** under `colorScheme: 'light'` and `colorScheme: 'dark'`, confirming the emulation
had no effect.

**Failure scenario:** a reader relies on this line as evidence that the credential renders correctly
in dark mode, when the scenario was never actually exercised.

**Why non-blocking:** (a) I found no theme switcher anywhere in `src/` (no `next-themes`, no
`documentElement.classList` manipulation), so the `.dark` class appears unreachable in the running
app; (b) the canonical credential is positioned off-screen and is `type="password"`, so its visual
styling is immaterial in any scheme; (c) the reduced-motion half of the claim is valid — I confirmed
`prefers-reduced-motion: reduce` matches and fill/unlock still work. The claim is unsupported, not
false in a way that hides a defect.

### NB-5 (NON-BLOCKING, secret hygiene — new artifact surface, no leak) — Playwright accessibility snapshots now capture the real phrase

New observation, not raised in the evidence. Playwright's page snapshot renders the **value** of the
canonical `type="password"` field into its YAML artifact. Running
`playwright-cli -s=<session> click <generate>` on `/new-user` wrote a file containing
`- textbox "Recovery phrase" [ref=…]: <the twelve generated words>`.

This is a change in exposure surface relative to BASE. At BASE, `/new-user` renders with
`initiallyRevealed={false}` (`src/app/(onboarding)/new-user/page.tsx:216`), so the grid cells
snapshot as `•••••` and the generated phrase did **not** reach a snapshot artifact. The canonical
field introduced by `RecoveryPhraseCredentialFields.tsx:110-124` holds the plaintext phrase as its
DOM value, and that value is what the snapshotter serializes.

**Failure scenario:** an agent or CI job snapshots `/new-user`, the artifact is later attached to a
ticket, copied into an evidence file, or uploaded, and a real recovery phrase leaks.

**Why non-blocking:** (a) `.playwright-cli/` and `test-results/` are both gitignored
(`.gitignore:39-40`), so nothing is committed; (b) the phrase being present in the DOM as a password
value is _precisely the mechanism HS-019 requires_ — it cannot be removed without defeating the
requirement; (c) no leak occurred: I deleted the artifact directory, and I verified nothing entered
git, logs, URLs, network payloads, or storage. This is a tooling-hygiene note for future
agents/packages, not a product defect. **Recommendation for root:** future manual charters on
`/new-user` should delete `.playwright-cli/` afterwards, as this implementer did and as I did.

### NB-6 (NON-BLOCKING, pre-existing — explicitly NOT a P18 regression) — controlled-mode gap collapse

Typing into word slot 3 while slot 2 is empty causes the word to migrate into slot 2. Observed live
on `/unlock`: typing `abandon` into word 1, then `about` into word 3, yields
`words = ["abandon","a","bout",…]` — the value visibly walks forward character by character.

Root cause is the controlled round-trip: `joinWordSlotsIntoPhrase`
(`recoveryPhraseCredential.ts:53`) drops empty slots, `UnlockCircle` feeds the joined phrase back as
`value` (`UnlockCircle.tsx:165`), and the re-split re-packs the words leftward.

**I verified this is pre-existing and byte-identical at BASE.** I wrote a differential test and ran
it in a BASE worktree and at HEAD:

```
BASE:  expected [ 'abandon', 'about', '' ] to deeply equal [ 'abandon', '', 'about' ]  (fails)
HEAD:  expected [ 'abandon', 'about', '' ] to deeply equal [ 'abandon', '', 'about' ]  (fails)
```

Identical failure. BASE's `newWords.join(" ").trim()` followed by `split(/\s+/)` collapses the gap
exactly as the new helpers do; P18 refactored the behavior into named pure functions without
changing it. The uncontrolled case passes at both revisions.

**Failure scenario:** a user filling the grid out of order sees words jump slots.

**Why non-blocking:** not introduced by this package, out of HS-019 scope, and it does not affect
the manager save/fill contract (a manager always fills the complete phrase in one write, which
round-trips exactly — verified). Recorded so root can route it to a future package if desired.
