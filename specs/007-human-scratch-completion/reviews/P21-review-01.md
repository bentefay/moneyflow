### 5A. BLOCKING — `identity.spec.ts:282` hydration-timing flake (independently confirmed)

- **Failure:** `expect(validClasses).not.toBe(invalidClasses)` at `identity.spec.ts:365`. In my run
  #2 both reads captured the identical NEUTRAL class string
  (`border-input … bg-background/80 font-mono`), lacking the directly-applied `border-destructive`
  (invalid) or `border-green-500` (valid) classes. `aria-invalid:border-destructive` present in the
  string is a Tailwind variant selector, not the applied validity class.
- **Product is CORRECT.** `src/components/features/identity/SeedPhraseInput.tsx` derives
  `wordValidation` via a synchronous `useMemo` on `words` (`:120`), then applies
  `border-green-500 focus-visible:ring-green-500` when `showValid` (`:344`) and
  `border-destructive focus-visible:ring-destructive` when `showError` (`:342-343`). A valid and an
  invalid word therefore render different classes by construction. No product defect.
- **Mechanism (test-quality race):** the twelve slots are controlled React inputs (`value={word}`).
  When Playwright's `fill()` lands before React hydration commits, the DOM value is set but
  `onChange` never fires, so `words` state / the memo-driven className never update. The test's
  guards `toBeEditable()` + `toHaveValue()` are INSUFFICIENT: a controlled input can expose the
  filled DOM value pre-hydration while its className still holds the neutral SSR string — so both
  reads capture the same neutral class and the assertion fails. The test comment (`:349-353`) itself
  documents this race; the guards do not close it (they check value presence, not that the validity
  class changed).
- **Rate:** 1 failure in 2 full-suite runs under my audit (matches the collector's 1-in-2). It
  manifests only under full 163-test parallel load; targeted isolation is green.
- **Classification:** a NEW, UNDOCUMENTED E2E flake — NOT Q-P20B-13 (`import.spec.ts:301` vault
  race) and NOT Q-P20A-05 (`duplicates` unit). It broke the retries-disabled final-audit full-suite
  run.
- **Why blocking:** GOAL DoD requires the complete E2E suite to pass clean with no accepted
  unexplained flake, and DoD requires "all changed E2E journeys pass repeated, retries-disabled
  flake checks"; the P21 contract makes a NEW flake blocking. A documented NEW retries-disabled
  failure is blocking even where it does not reproduce on the first rerun — and here it DID
  reproduce independently.

The two tracked residuals behaved as documented: `import.spec.ts:301` PASSED in both my E2E runs;
`duplicates.test.ts` is the Q-P20A-05 unit flake (passes in isolation).
